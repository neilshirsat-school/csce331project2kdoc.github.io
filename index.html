CSCE 331 Project 2 — Bubble-Tea POS + Inventory

A Kotlin/Gradle desktop scaffold for the waterfall POS and inventory project. Both user-facing modules are JavaFX desktop applications; shared business/data code is isolated from UI code.

Modules

  • app-cashier: JavaFX order-entry shell with menu, cart, totals, pay, and void placeholders.

  • app-manager: JavaFX shell for trends, inventory, and restock sections.

  • lib-ui: reusable JavaFX controls and theme; contains no business rules or JDBC.

  • lib-logic: domain models, mock menu catalog service/repository, service interfaces, JDBC configuration/repository skeletons; contains no JavaFX.

  • lib-database: Exposed JDBC database access, Exposed Table objects for the POS schema, and the bundled PostgreSQL schema assets.

The manager's Inventory view includes replenishment amounts in the ingredient table and pairs recent shipments with product usage for the last 30 days. The cards share a height and stack on narrow windows. Reports contains the X-report's daily totals and hourly breakdown. Both standalone application distributions include the other view at runtime so manager/cashier switching works when launched through either module's run task or installed script.

Click an ingredient to open its inventory drawer. Replenish creates a submitted purchase order for the shortage below the notify-at level, subtracting quantities already on pending orders. It uses the ingredient's current unit cost and records the signed-in employee; stock changes when the order is received. The Menu and Employees tables fill the remaining page height and scroll their rows independently.

The inventory drawer edits ingredient details directly in a table; save changes before replenishing. On-hand corrections and metadata are saved together. Cashier customization navigation is temporarily disabled: clicking a card or its add button adds the default drink. Recipe drawers omit allergen information. Manager and cashier category filters use the categories present in their catalog items, and the manager menu form uses those same names. Ingredient creation uses the supported ingredient/supply category selector. X-report and employee performance tables share numeric alignment and table spacing.

The cashier depends on lib-ui, lib-logic, and lib-database; the manager currently depends on lib-ui and lib-logic. All Kotlin packages use the sh.snt namespace, with shared UI components under sh.snt.ui and icons under sh.snt.ui.icons.

The cashier view is based on the supplied reference: category chips, searchable drink cards, an order summary panel, and a warm neutral POS theme. With POS_DB_URL configured, the cashier loads its menu through the Exposed query layer, including each item's image_url and image_path. Menu cards and the item detail view show the cached image first, then use the source URL if the local image file is unavailable. Without a configured database, the app uses the mock menu and shows the patterned placeholder for entries without image data. The shared icon components use Phosphor regular-weight SVG path shapes and are kept in lib-ui; see Phosphor Icons for the source icon family and license.

Haskoy is bundled under lib-ui/src/main/resources/fonts with its SIL Open Font License and author notices. The Haskoy variable TTF and static Regular/Medium/Bold fallback faces are loaded locally by UiKit before the JavaFX scene is shown, so the application does not fetch fonts over the network. JavaFX CSS maps UI roles to explicit normal/bold weights; the static faces ensure those weights remain visible on JavaFX versions that do not apply variable-font axes through CSS. The JavaFX root size is 14px, equivalent to 0.875rem in a 16px design system, and UI text does not go below 11px. The cashier order tabs use a full-width animated indicator, and interactive controls include hover and pressed-state feedback.

Database configuration

Startup requires a configured endpoint. If none is present, the launcher keeps the shared sign-in page visible; the masked-password setup dialog opens only after an explicit Database settings action. The dialog tests asynchronously and can save non-secret endpoint settings to $HOME/.share-tea/.env (passwords are never persisted there). Environment variables take precedence over a repository-root .env, which takes precedence over the per-user file. The checked-in .env.example template is never read as credentials. Settings can be reset by removing the per-user file or choosing a new endpoint in the dialog. A packaged launch uses the same per-user location; ./run-app.sh cashier and ./run-app.sh manager remain the supported launch commands. SSL defaults to prefer, not require. Unreachable endpoints can be recovered with Retry/Edit in the setup dialog; check host, port, database, credentials, firewall access, and PostgreSQL SSL mode when troubleshooting.

No secrets are committed. The JDBC scaffold reads:

  • POS_DB_URL (optional complete JDBC URL), or POS_DB_HOST, POS_DB_PORT, and POS_DB_NAME

  • POS_DB_USER and POS_DB_PASSWORD

  • POS_DB_SSLMODE (default prefer) and POS_DB_READ_ONLY=true for safe inspection

The equivalent libpq names (PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD, and PGSSLMODE) are accepted. Passwords are read from the process environment only and are never printed or placed in source, reports, screenshots, or test artifacts. PosDatabaseConfig.fromEnvironment() builds the JDBC URL and adds PostgreSQL's transaction-level read-only default when POS_DB_READ_ONLY is enabled.

The deployed course database uses the condensed ten-table schema. Desktop clients access it through PosRepositories, which detects the available columns and tables. Categories, role assignments, password hashes, inventory balances, and payment methods are stored inline in that schema. Receiving uses the existing purchase-order trigger. See SCHEMA_COMPATIBILITY.md for report mappings and isolated PostgreSQL regression-test instructions.

design.sql defines the original 51-table local fixture. The module defines an Exposed Table object for every fixture table and uses SchemaUtils.create() to build those tables, including their columns, primary and foreign keys, unique indexes, generated columns, identity columns, and check constraints. It then applies supporting.sql for PostgreSQL views, indexes, functions, and triggers. Both files are bundled as /db/design.sql and /db/supporting.sql; schema creation uses the Exposed objects for tables and the supporting script for PostgreSQL-specific objects. PosDatabase.createSchemaIfEmpty() runs transactionally when the active schema has no tables. PosViews contains read-only mappings for the three fixture reporting views. When working against this original fixture, database work runs in PosDatabase.transaction { ... }; import a table object and use Exposed's DSL to query or update it:

import org.jetbrains.exposed.v1.jdbc.selectAll
import org.jetbrains.exposed.v1.core.eq
import sh.snt.database.PosDatabase
import sh.snt.database.tables.StoresTable

val activeStores = PosDatabase().transaction {
    StoresTable.selectAll().where { StoresTable.isActive eq true }.toList()
}

PosTables.all lists all 51 base table objects. PosViews.all lists the three read-only view mappings.

sh.snt.database.query.SupportingQueries provides typed Exposed queries for cash_history, inventory_history, inventory_on_hand, and unresolved low-stock alerts. For example, SupportingQueries.inventoryHistory(storeId = 1, rawItemId = 8) returns an Exposed Query that can be consumed inside PosDatabase.transaction { ... }. The dry-run test prepares each query with Exposed and asks an in-memory H2 database for an EXPLAIN plan; it does not modify data or require PostgreSQL.

The read-only schema comparison for the pinned condensed course schema is in SCHEMA_COMPATIBILITY.md. It documents the users, roles, password-hash, sales, inventory, and allergen coverage matrix, the observed shared-database inspection, and the local-fixture/additive-migration boundary. lib-database/src/main/resources/db/compatibility.sql is a review note only; it is deliberately not applied automatically.

The complete cashier and manager read-query inventory is documented in lib-database/QUERY_CATALOG.md. CashierQueries, ManagerQueries, and SupportingQueries expose all 66 catalogued query builders.

Add implementation(project(":lib-database")) to an app or library that needs persistence. lib-database uses JetBrains Exposed 1.5.0 (exposed-jdbc) and PostgreSQL JDBC. Its Kotlin sources are formatted with Spotless and ktlint: run ./gradlew :lib-database:spotlessApply to format or ./gradlew :lib-database:spotlessCheck to check formatting.

In-process view shortcuts

After authentication, manager/dual-role users can switch destinations in the same window with Ctrl+Shift+M (Manager) and Ctrl+Shift+C (Cashier). The profile menu exposes the same actions. Architecture

Share Tea POS is a multi-module Kotlin/JVM desktop application. Modules are deliberately layered so that business rules stay independent of JavaFX and database technology.

Layering rules

  1. UI depends inward. JavaFX code may call lib-logic services and lib-database repositories, but no lower layer imports JavaFX.

  2. Pure rules stay pure. Pricing, payment validation, inventory status, category filtering, and report aggregation live in sh.snt.logic.service and are directly unit-testable.

  3. Repositories are contracts. sh.snt.logic.repo defines interfaces used by services; sh.snt.database.repository provides JDBC/Exposed adapters.

  4. Tables mirror PostgreSQL. Exposed Table objects in sh.snt.database.tables are the single source of truth for column names, defaults, and foreign keys.

  5. Schema compatibility is explicit. Bootstrap and reporting code probe for optional views/tables before using them, so older databases keep working.

Runtime flow

  1. PosLauncher installs the shared sign-in scene and starts a background connection probe.

  2. Successful authentication publishes an AuthenticatedUser through StartupHandoff.

  3. The launcher opens ManagerApp when the user can manage, otherwise CashierApp when the user can sell.

  4. Both shells load data through repositories and fall back to local fixtures when the database is unavailable (cashier menu only).

Domain model and business rules

This page summarizes the concepts shared by both desktop shells. The canonical types live in sh.snt.logic.model and sh.snt.logic.service.

Money

All monetary amounts are integer cents (Int) at the UI and order layer, and NUMERIC/BigDecimal at the database and reporting layer. Convert only at the boundary:

  • OrderService.totals returns OrderTotals in cents.

  • PaymentService.parseAmount converts user text to cents, rejecting more than two decimal places.

  • SalesAnalyticsService returns BigDecimal amounts rounded half-up to two decimal places.

Orders

val order = OrderService()
    .addItem(Order(), item = latte, quantity = 2)
    .let { orderService.updateQuantity(it, lineIndex = 0, quantity = 3) }

val totals = orderService.totals(order, discountCode = "BOBA10")
Content copied to clipboard

Order and OrderLine are immutable value objects. Every editing operation returns a new instance, which keeps undo/redo and JavaFX state updates simple.

Inventory

CartInventory is a read-only snapshot of ingredient stock and per-serving recipe requirements. It derives requirements for a cart, reports shortages, and computes how many additional servings can be made. It never writes reservations to the database; availability is re-validated during checkout.

Inventory quantities accept at most three decimal places to match NUMERIC(12,3). The low-stock threshold is inclusive: onHand <= notifyAt is considered low.

Authentication

Passwords are hashed with PBKDF2-HMAC-SHA256 and per-user salts. Authentication results distinguish success, invalid credentials, and disabled accounts. AuthenticatedUser exposes role and permission sets used by the launcher to select the manager or cashier shell.

Reporting

Reports are computed from immutable sale snapshots. Voids and open orders are excluded; refunds reduce net sales without creating a second order. Date ranges are half-open: [fromInclusive, untilExclusive).
